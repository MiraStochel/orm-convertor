How a translation works

The examples on this page are live: each one is a set of input files the server hands out, sent to the same /convert endpoint the translator uses and shown with the real output next to the real input. They cannot drift away from the tool, because the tool produces them.

The pipeline

Every conversion has the same three phases. A framework-specific parser reads the source artifacts — entity classes, mapping files, queries — into a framework-agnostic intermediate representation. If a database catalog connection is configured on the server, a completion phase fills in mapping facts the source never stated (column types, keys, foreign keys) and records where each fact came from. Finally a framework-specific builder generates the target artifacts, validating against what the target can express. Anything dropped, filled in by convention, or supplied by the catalog becomes a structured record returned next to the artifacts.

The examples

Ten examples. The first seven are grouped by the boundary the translation crosses: two stay inside .NET, two inside Java, and three cross between the ecosystems — the last two over a whole domain rather than a single class. The other three are about queries: what a target does with a construct its query language lacks, and how the queries are found in code. Below each one, the records list every place where the output could not carry a fact of the input, or states something the input did not. That is where a translation explains itself.

Within Java

Both examples start from the same Hibernate project: a customer whose key the framework generates, a national column written with Hibernate's own annotation, a version column, and a query that takes one page of results with the limit clause only HQL has. Whatever differs between the two outputs is the difference between the two targets.

Hibernate → EclipseLink

Two implementations of one specification read the same annotations, so everything the source states travels unchanged. What differs is what the source leaves unsaid. A bare @GeneratedValue means a sequence to Hibernate and a counter table to EclipseLink; @Nationalized is Hibernate's own annotation and EclipseLink has none; limit and offset exist only in HQL. The artifact therefore writes each of them out — the counter table in full, the national column as a literal nvarchar(200), the page of results on the query object. The two conventions in the records name the first two places; the page needs no record, because on the query object it selects the same rows as in the text.

Hibernate → MyBatis

The same input, towards the other end of the Java ecosystem. MyBatis maps results rather than tables: the entity becomes a plain class that imports nothing from the framework, and the mapping shrinks to pairs of column and property in a result map. The query turns into SQL inside a mapper document — entity and attribute names become the table and its columns, the parameter becomes #{…}, the page becomes OFFSET … FETCH — and a mapper interface declares the method with its typed parameter. Everything the mapper has no place for — the table, lengths, precision, nullability, key generation, the version column — is a loss in the records, one line per fact.

Across the ecosystems

MyBatis → Dapper

Two frameworks that both keep SQL as it is, one on each side of the boundary. The statements travel as T-SQL: the <include> fragment and the <where> element are expanded, #{creditLimit} becomes @creditLimit, and each statement becomes a Dapper method named after its id. The parameter's type is not in the SQL at all — it comes from the Java mapper interface, where BigDecimal creditLimit becomes decimal creditLimit. The records show the other side of the bargain: a Dapper class has no place for column names or types, and a MyBatis <id> marks the identity of a result row, not the primary key of a table.

Whole domains

A real project hands over a domain, not a class, and some phases of the pipeline only run when there are several entities: a relation is paired with the key it points to, a many-to-many gets its junction entity, a composite key gets the members its target requires. The two examples below are larger, one in each direction across the ecosystems. Their input and output are folded because they carry dozens of files; open them from the summaries. Every generated query method is called Query or query: a LINQ method's or a JPQL file's own name is not read as the name of its query, so the output panels follow the order of the input files.

Order book: EF Core → Hibernate

Four annotated EF Core entities and six LINQ queries become JPA entities and JPQL. The order line is keyed by its order and its number, and the first part of that key is at the same time the foreign key to the order: the key becomes @IdClass with a nested key class, and the relation over that column is kept from writing it (insertable = false). Every [ForeignKey] is paired with the key of the entity it points to, unique indexes become @UniqueConstraint, the row version becomes @Version and the unmapped property @Transient. In the queries, captured variables become named parameters, Skip and Take move to the query object, a GroupBy followed by Where becomes having, Any and Contains over another set become exists and in subqueries, Average becomes a scalar subquery, and Union stays a union.

Lending library: Hibernate → NHibernate

The opposite direction over a second domain: five annotated Java entities and five JPQL queries become C# classes, hbm.xml mappings and HQL. The many-to-many between books and authors is declared by @JoinTable and has no class of its own in Java; NHibernate gets it as an explicit junction entity, BookAuthor, with a composite key and two many-to-one relations. A copy of a book is keyed by two columns through @IdClass, which becomes a <composite-id> and the Equals, GetHashCode and [Serializable] NHibernate requires of it; a loan points at that copy through both columns, in their order. The sequence keeps its name and schema, the version column becomes <version>, and the literal char(2) survives as an sql-type. In the queries, the entity join becomes join … with, a collection parameter goes through SetParameterList, between becomes two comparisons, and the page given by limit and offset moves to SetFirstResult and SetMaxResults, because HQL has no clause for it.

Queries

A query in the intermediate representation can say more than the part all six query languages share: a result that another query reads (a common table expression or a derived table), recursion, a ranking over a window, a list joined from the values of a group, arithmetic over dates. A target whose query language has the construct writes it there. A target whose language lacks it writes the whole query in the native SQL of its database, through its framework's own API, and a Fallback record names the construct that sent it there — a native query is never passed off as a translation. A query a target can say neither in its language nor in native SQL is refused there with a Failure record; the LDBC page shows the one such case among its 41 queries.

The input of these three examples is what a project has: a class that hands its queries to the framework. Such a class is read as the code around the queries, not as an entity, and every place where it hands a query over is one query of the conversion, named by its position in the text — Query01, Query02, … (query01 in Java). The query methods close the output, after the entities.

Reports: Hibernate → EF Core

Five reports over the lending library, each a method of one Java class that hands a query of HQL 7.4 to the framework; the last one walks a sixth entity, a hierarchy of genres. Three of them EF Core says in LINQ. The common table expression becomes a variable of the method, which the query reads twice — in the join and in the subquery that averages it. The list of titles becomes string.Join over the ordered titles of each group, and the days a book was out become EF.Functions.DateDiffDay. The other two LINQ cannot say: it has no ranking over a window, and a variable cannot name itself, so it has no recursion. Those two go out as native SQL through Database.SqlQuery, with a row class written from the projection and the parameter as an interpolated hole, which EF Core binds as a parameter rather than as text; a Fallback record stands beside each. Most of the other records are the entities': the annotations of EF Core state neither an identity nor a sequence, nor a version the framework increments.

Reports: Hibernate → NHibernate

The same input towards NHibernate, so whatever differs from the example above is the difference between the two query languages. HQL of NHibernate 5.7 has none of the five constructs — no with, no window, no list aggregate, no date arithmetic — so all five reports go out as native SQL through CreateSQLQuery, the parameters as :name and an AddScalar for every column, so that the rows come back typed. Five queries carry six Fallback records: the report over the genres names both of its reasons, the common table expression and its recursion. The entities and their mappings are those of the lending library above, and the genre joins them with an assigned key, because the source states no generation, and its parent as a many-to-one beside the column it shares.

Order repository: EF Core → EclipseLink

A repository over the order book: one C# file, five methods, each handing a query to EF Core in another way. A chain stored in a variable that the code assigns once and then extends is read as the one tree the provider receives. FirstOrDefault is read as a page of one row, and a Convention record says what the artifact leaves out: the caller receives a single value, the generated method a query of at most one row. A query expression with a second from over a navigation becomes a join whose condition comes from the mapping. An explicit load — Entry(order).Collection(o => o.Lines).Query() — is read as the query the provider composes: the lines whose foreign key equals the key of the order in memory, bound as the parameter SalesOrderId. And native SQL handed to Database.SqlQuery is read as a query like any other, so EclipseLink receives it as JPQL, with the column ShipToCity back as the attribute City. JPQL says all five, so nothing falls back.
