How a translation works

The examples on this page are live: each one loads a built-in sample, sends it to the same /convert endpoint the translator uses, and shows the real output next to the real input. They cannot drift away from the tool, because the tool produces them.

The pipeline

Every conversion has the same three phases. A framework-specific parser reads the source artifacts — entity classes, mapping files, queries — into a framework-agnostic intermediate representation. If a database catalog connection is configured on the server, a completion phase fills in mapping facts the source never stated (column types, keys, foreign keys) and records where each fact came from. Finally a framework-specific builder generates the target artifacts, validating against what the target can express. Anything dropped, filled in by convention, or supplied by the catalog becomes a structured record returned next to the artifacts.

Example 1: EF Core → NHibernate

The source states a lot: an EF Core entity annotated with attributes (table, column types, keys) and a LINQ query. Watch how the attributes become an NHibernate XML mapping, how the entity class loses its attributes but gains what NHibernate enforces (virtual members), and how the LINQ chain becomes HQL. The records tell you every place where the target could not carry a fact, or where a gap was filled by a convention.

Example 2: Dapper → EF Core

The opposite direction: the source states very little. A Dapper entity is a plain C# class and the query is raw SQL, so most mapping facts — table names, key, column types — are nowhere in the input. The generated EF Core artifacts therefore lean on conventions (or on the database catalog, when the server has a connection configured), and the records are where you see it happen: this is the example that shows what the diagnostics are for.
