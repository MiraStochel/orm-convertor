How a translation works

The examples on this page are live: each one is a set of input files the server hands out, sent to the same /convert endpoint the translator uses and shown with the real output next to the real input. They cannot drift away from the tool, because the tool produces them.

The pipeline

Every conversion has the same three phases. A framework-specific parser reads the source artifacts — entity classes, mapping files, queries — into a framework-agnostic intermediate representation. If a database catalog connection is configured on the server, a completion phase fills in mapping facts the source never stated (column types, keys, foreign keys) and records where each fact came from. Finally a framework-specific builder generates the target artifacts, validating against what the target can express. Anything dropped, filled in by convention, or supplied by the catalog becomes a structured record returned next to the artifacts.

The examples

Seven examples, grouped by the boundary the translation crosses: two stay inside .NET, two inside Java, and three cross between the ecosystems — the last two over a whole domain rather than a single class. Below each one, the records list every place where the output could not carry a fact of the input, or states something the input did not. That is where a translation explains itself.

Within Java

Both examples start from the same Hibernate project: a customer whose key the framework generates, a national column written with Hibernate's own annotation, a version column, and a query that takes one page of results with the limit clause only HQL has. Whatever differs between the two outputs is the difference between the two targets.

Hibernate → EclipseLink

Two implementations of one specification read the same annotations, so everything the source states travels unchanged. What differs is what the source leaves unsaid. A bare @GeneratedValue means a sequence to Hibernate and a counter table to EclipseLink; @Nationalized is Hibernate's own annotation and EclipseLink has none; limit and offset exist only in HQL. The artifact therefore writes each of them out — the counter table in full, the national column as a literal nvarchar(200), the page of results on the query object — and the two conventions in the records name exactly those places.

Hibernate → MyBatis

The same input, towards the other end of the Java ecosystem. MyBatis maps results rather than tables: the entity becomes a plain class that imports nothing from the framework, and the mapping shrinks to pairs of column and property in a result map. The query turns into SQL inside a mapper document — entity and attribute names become the table and its columns, the parameter becomes #{…}, the page becomes OFFSET … FETCH — and a mapper interface declares the method with its typed parameter. Everything the mapper has no place for — the table, lengths, precision, nullability, key generation, the version column — is a loss in the records, one line per fact.

Across the ecosystems

MyBatis → Dapper

Two frameworks that both keep SQL as it is, one on each side of the boundary. The statements travel as T-SQL: the <include> fragment and the <where> element are expanded, #{creditLimit} becomes @creditLimit, and each statement becomes a Dapper method named after its id. The parameter's type is not in the SQL at all — it comes from the Java mapper interface, where BigDecimal creditLimit becomes decimal creditLimit. The records show the other side of the bargain: a Dapper class has no place for column names or types, and a MyBatis <id> marks the identity of a result row, not the primary key of a table.

Whole domains

A real project hands over a domain, not a class, and some phases of the pipeline only run when there are several entities: a relation is paired with the key it points to, a many-to-many gets its junction entity, a composite key gets the members its target requires. The two examples below are larger, one in each direction across the ecosystems. Their input and output are folded because they carry dozens of files; open them from the summaries. Every generated query method is called Query or query: a LINQ method's or a JPQL file's own name is not read as the name of its query, so the output panels follow the order of the input files.

Order book: EF Core → Hibernate

Four annotated EF Core entities and six LINQ queries become JPA entities and JPQL. The order line is keyed by its order and its number, and the first part of that key is at the same time the foreign key to the order: the key becomes @IdClass with a nested key class, and the relation over that column is kept from writing it (insertable = false). Every [ForeignKey] is paired with the key of the entity it points to, unique indexes become @UniqueConstraint, the row version becomes @Version and the unmapped property @Transient. In the queries, captured variables become named parameters, Skip and Take move to the query object, a GroupBy followed by Where becomes having, Any and Contains over another set become exists and in subqueries, Average becomes a scalar subquery, and Union stays a union.

Lending library: Hibernate → NHibernate

The opposite direction over a second domain: five annotated Java entities and five JPQL queries become C# classes, hbm.xml mappings and HQL. The many-to-many between books and authors is declared by @JoinTable and has no class of its own in Java; NHibernate gets it as an explicit junction entity, BookAuthor, with a composite key and two many-to-one relations. A copy of a book is keyed by two columns through @IdClass, which becomes a <composite-id> and the Equals, GetHashCode and [Serializable] NHibernate requires of it; a loan points at that copy through both columns, in their order. The sequence keeps its name and schema, the version column becomes <version>, and the literal char(2) survives as an sql-type. In the queries, the entity join becomes join … with, a collection parameter goes through SetParameterList, between becomes two comparisons, and the page given by limit and offset moves to SetFirstResult and SetMaxResults, because HQL has no clause for it.
