How a translation works

The examples on this page are live: each one is a set of input files the server hands out, sent to the same /convert endpoint the translator uses and shown with the real output next to the real input. They cannot drift away from the tool, because the tool produces them. The base input before them is shown as the server hands it out, for any target.

The pipeline

Every conversion has the same three phases. A framework-specific parser reads the source artifacts — entity classes, mapping files, queries — into a framework-agnostic intermediate representation. If a database catalog connection is configured on the server, a completion phase fills in mapping facts the source never stated (column types, keys, foreign keys) and records where each fact came from. Finally a framework-specific builder generates the target artifacts, validating against what the target can express. Anything dropped, filled in by convention, or supplied by the catalog becomes a structured record returned next to the artifacts.

The base input

One customer, written in each of the six frameworks. It is not an example of a direction: it is the base input, and it goes into any of the six targets, its own framework included. On the Translation page it is the first six entries of the example list, one per framework. Dapper and MyBatis have no place for a key, so into NHibernate, Hibernate and EclipseLink they go only where the server reads the database catalog, which supplies it.

The examples

Twenty-one examples. The first seven are grouped by the boundary the translation crosses: two stay inside .NET, two inside Java, and three cross between the ecosystems — the last two over a whole domain rather than a single class. The next three are about queries: what a target does with a construct its query language lacks, and how the queries are found in code. The next four take one larger domain, a marketplace, from four source frameworks, and together show what the tool reads and writes — one of them is a single, very long query. The next two are application code as a project has it, where the mapping and the queries are a small part of the text, and show what the tool takes out of it. The last five are not written for the tool at all: they are excerpts of real open-source projects, taken at one commit and changed only where the tool reads a construct in another form. Below each one, the records list every place where the output could not carry a fact of the input, or states something the input did not. That is where a translation explains itself.

Every example is also in the list on the Translation page, below the base input: Load example puts its files into the editor and sets the direction it is described for, and from there the target can be switched to any of the six.

Within Java

Both examples start from the same Hibernate project: a customer whose key the framework generates, a national column written with Hibernate's own annotation, a version column, and a query that takes one page of results with the limit clause only HQL has. Whatever differs between the two outputs is the difference between the two targets.

Hibernate → EclipseLink

Two implementations of one specification read the same annotations, so everything the source states travels unchanged. What differs is what the source leaves unsaid. A bare @GeneratedValue means a sequence to Hibernate and a counter table to EclipseLink; @Nationalized is Hibernate's own annotation and EclipseLink has none; limit and offset exist only in HQL. The artifact therefore writes each of them out — the counter table in full, the national column as a literal nvarchar(200), the page of results on the query object. The two conventions in the records name the first two places; the page needs no record, because on the query object it selects the same rows as in the text.

Hibernate → MyBatis

The same input, towards the other end of the Java ecosystem. MyBatis maps results rather than tables: the entity becomes a plain class that imports nothing from the framework, and the mapping shrinks to pairs of column and property in a result map. The query turns into SQL inside a mapper document — entity and attribute names become the table and its columns, the parameter becomes #{…}, the page becomes OFFSET … FETCH — and a mapper interface declares the method with its typed parameter. Everything the mapper has no place for — the table, lengths, precision, nullability, key generation, the version column — is a loss in the records, one line per fact.

Across the ecosystems

MyBatis → Dapper

Two frameworks that both keep SQL as it is, one on each side of the boundary. The statements travel as T-SQL: the <include> fragment and the <where> element are expanded, #{creditLimit} becomes @creditLimit, and each statement becomes a Dapper method named after its id. The parameter's type is not in the SQL at all — it comes from the Java mapper interface, where BigDecimal creditLimit becomes decimal creditLimit. The records show the other side of the bargain: a Dapper class has no place for column names or types, and a MyBatis <id> marks the identity of a result row, not the primary key of a table.

Whole domains

A real project hands over a domain, not a class, and some phases of the pipeline only run when there are several entities: a relation is paired with the key it points to, a many-to-many gets its junction entity, a composite key gets the members its target requires. The two examples below are larger, one in each direction across the ecosystems. Their input and output are folded because they carry dozens of files; open them from the summaries. Every generated query method is called Query or query: a LINQ method's or a JPQL file's own name is not read as the name of its query, so the output panels follow the order of the input files.

Order book: EF Core → Hibernate

Four annotated EF Core entities and six LINQ queries become JPA entities and JPQL. The order line is keyed by its order and its number, and the first part of that key is at the same time the foreign key to the order: the key becomes @IdClass with a nested key class, and the relation over that column is kept from writing it (insertable = false). Every [ForeignKey] is paired with the key of the entity it points to, unique indexes become @UniqueConstraint, the row version becomes @Version and the unmapped property @Transient. In the queries, captured variables become named parameters, Skip and Take move to the query object, a GroupBy followed by Where becomes having, Any and Contains over another set become exists and in subqueries, Average becomes a scalar subquery, and Union stays a union.

Lending library: Hibernate → NHibernate

The opposite direction over a second domain: five annotated Java entities and five JPQL queries become C# classes, hbm.xml mappings and HQL. The many-to-many between books and authors is declared by @JoinTable and has no class of its own in Java; NHibernate gets it as an explicit junction entity, BookAuthor, with a composite key and two many-to-one relations. A copy of a book is keyed by two columns through @IdClass, which becomes a <composite-id> and the Equals, GetHashCode and [Serializable] NHibernate requires of it; a loan points at that copy through both columns, in their order. The sequence keeps its name and schema, the version column becomes <version>, and the literal char(2) survives as an sql-type. In the queries, the entity join becomes join … with, a collection parameter goes through SetParameterList, between becomes two comparisons, and the page given by limit and offset moves to SetFirstResult and SetMaxResults, because HQL has no clause for it.

Queries

A query in the intermediate representation can say more than the part all six query languages share: a result that another query reads (a common table expression or a derived table), recursion, a ranking over a window, a list joined from the values of a group, arithmetic over dates. A target whose query language has the construct writes it there. A target whose language lacks it writes the whole query in the native SQL of its database, through its framework's own API, and a Fallback record names the construct that sent it there — a native query is never passed off as a translation. A query a target can say neither in its language nor in native SQL is refused there with a Failure record — none of the 41 queries on the LDBC page is.

The input of these three examples is what a project has: a class that hands its queries to the framework. Such a class is read as the code around the queries, not as an entity, and every place where it hands a query over is one query of the conversion, named by its position in the text — Query01, Query02, … (query01 in Java). The query methods close the output, after the entities.

Reports: Hibernate → EF Core

Five reports over the lending library, each a method of one Java class that hands a query of HQL 7.4 to the framework; the last one walks a sixth entity, a hierarchy of genres. Three of them EF Core says in LINQ. The common table expression becomes a variable of the method, which the query reads twice — in the join and in the subquery that averages it. The list of titles becomes string.Join over the ordered titles of each group, and the days a book was out become EF.Functions.DateDiffDay. The other two LINQ cannot say: it has no ranking over a window, and a variable cannot name itself, so it has no recursion. Those two go out as native SQL through Database.SqlQuery, with a row class written from the projection and the parameter as an interpolated hole, which EF Core binds as a parameter rather than as text; a Fallback record stands beside each. Most of the other records are the entities': the annotations of EF Core state neither an identity nor a sequence, nor a version the framework increments.

Reports: Hibernate → NHibernate

The same input towards NHibernate, so whatever differs from the example above is the difference between the two query languages. HQL of NHibernate 5.7 has none of the five constructs — no with, no window, no list aggregate, no date arithmetic — so all five reports go out as native SQL through CreateSQLQuery, the parameters as :name and an AddScalar for every column, so that the rows come back typed. Five queries carry six Fallback records: the report over the genres names both of its reasons, the common table expression and its recursion. None of them gets the LINQ form NHibernate writes beside its HQL: what HQL does not say, the LINQ provider, which translates into HQL, does not say either. The entities and their mappings are those of the lending library above, and the genre joins them with an assigned key, because the source states no generation, and its parent as a many-to-one beside the column it shares.

Order repository: EF Core → EclipseLink

A repository over the order book: one C# file, five methods, each handing a query to EF Core in another way. A chain stored in a variable that the code assigns once and then extends is read as the one tree the provider receives. FirstOrDefault is read as a page of one row, and a Convention record says what the artifact leaves out: the caller receives a single value, the generated method a query of at most one row. A query expression with a second from over a navigation becomes a join whose condition comes from the mapping. An explicit load — Entry(order).Collection(o => o.Lines).Query() — is read as the query the provider composes: the lines whose foreign key equals the key of the order in memory, bound as the parameter SalesOrderId. And native SQL handed to Database.SqlQuery is read as a query like any other, so EclipseLink receives it as JPQL, with the column ShipToCity back as the attribute City. JPQL says all five, so nothing falls back.

The marketplace

The first two examples are about the mapping: what each source says and how much of it the target can say back. The inputs run to a dozen files and the outputs to more, so the panes start folded.

Fluent configuration: EF Core → NHibernate

Most EF Core projects keep their classes plain and describe the tables in code. The source is nine entities in three files, a context whose OnModelCreating configures them one chain at a time, and a configuration class for the order lines that the context applies. The tool reads that code as a bounded subset, before any annotation, and the context and the configuration class are read as configuration, not as entities. Everything the chains state reaches the NHibernate mapping: the default schema on every class, ValueGeneratedNever as an assigned generator, HasColumnName as a column of its own, IsUnicode(false) as AnsiString, HasColumnType("char(2)") as an sql-type, the alternate key and the unique indexes as unique — over two columns as a unique-key whose name the tool makes up and says so —, the one-to-one as a unique many-to-one on the dependent side and a one-to-one on the other, the self-reference of the categories, and the composite keys of the order line and of the explicit junction entity as <composite-id> with the Equals, GetHashCode and [Serializable] NHibernate requires. The row version becomes <version>, and so does the concurrency token of the order, with a Convention record: NHibernate increments it itself, where the EF Core application kept it. Ignore leaves the property on the class and out of the mapping. Two calls lie outside the subset on purpose, HasDefaultValueSql and OnDelete, and each is a Loss record naming the call. The three queries come back as HQL and, beside it, as LINQ over session.Query<T>().

Mapping documents and named queries: NHibernate → MyBatis

The shop as an NHibernate project keeps it: the classes in one C# file without a single foreign-key property, a mapping document per class, and the queries in three places — a mapping document of named queries, one in HQL and one in SQL, a bare HQL file, and a class that hands HQL to the session with the page on the query object. The mappings use what hbm.xml offers: four generators (assigned, identity, a named sequence, hilo over a table of its own), a version, a key whose first part is a key-many-to-one, a literal sql-type, unique columns and a unique key over a column and a relation, and a many-to-many over a join table, which the target receives as the junction entity ProductTag. MyBatis maps results rather than tables, so the classes become plain Java and the mappings result maps; every fact a result map has no place for, from the table to the generator, is a Loss record, one line per fact, which is why the records run long here. The queries are where the source pays off: a join along an association (join o.Customer c) becomes an SQL join whose condition comes from the mapping, a named query keeps its name as the id of its <select> and the name of the mapper method, the SQL query stays SQL, and every parameter is typed — from <query-param>, or from the column it is compared with. The two queries the source does not name are called query.

The query vocabulary in fourteen reports: Hibernate → EF Core

Ten JPA entities and one Java class with fourteen reports, each resting on another construct: a bound prefix and an escaped wildcard; a collection parameter beside a list of values; grouping with a filter over the groups, ordered by an aggregate; a left join that finds customers without orders, and a full join; a scalar subquery in the projection under a page; the quantified comparisons > all and = any; a union; two common table expressions with a ranking window; a recursive one over the category tree; a list joined from a group; date arithmetic beside a CASE; grouping by an expression; grouping over a grouped result. Twelve of them EF Core says in LINQ: the bound prefix becomes EF.Functions.Like, the escaped wildcard a Contains, the collection parameter an IEnumerable whose Contains EF Core expands, the full join a LeftJoin concatenated with the unmatched rows of a RightJoin, > all an All over the projected amounts and = any an IN (a Convention record says so), the union Union, the list string.Join over the ordered values of each group, the date difference EF.Functions.DateDiffDay, extract(year …) .Year, and the derived table a variable of the method that the chain joins. LINQ has neither a window nor recursion, so the ranking and the category tree go out as native SQL through Database.SqlQuery, each with a row class and a Fallback record that names why. Load it on the Translation page and switch the target: towards NHibernate seven of the fourteen go out as native SQL, towards EclipseLink five, towards Hibernate none.

One long query: EclipseLink → EF Core

One report, as long as reports get: a dashboard of regional champions in plain JPQL, handed to EclipseLink with its page on the query object. The outer query joins eight entities, one of them by a left join over two columns, groups by region and customer, and projects thirteen aggregates — three over distinct values, one over a CASE, one under COALESCE — beside a scalar subquery. Its filter nests subqueries five levels deep, the deepest correlated with the outermost row, and holds an EXISTS, a NOT EXISTS over a join, IN and > any over subqueries, scalar comparisons, a list of values, a range, an escaped pattern and string functions; the filter over the groups nests two levels more. Fourteen subqueries in all. EF Core receives the whole of it as one LINQ chain: Join and LeftJoin calls that build the row, one Where whose subqueries are nested ctx.Set<T>() chains ending in Any, Contains, Average and Max, a GroupBy over an anonymous key, the filter over the groups as a second Where, a projection with Distinct().Count() and a coalesced Sum, then the ordering, Skip and Take. Nothing falls back and nothing is lost; beside the records of the entities the query adds two Conventions — the class is read as the code around its query, and the range became two comparisons. Load it on the Translation page and switch the target to see the same query as T-SQL for Dapper or MyBatis, as HQL with its LINQ form for NHibernate, or as JPQL for Hibernate and EclipseLink.

Application code

In a real project the mapping and the queries are a small part of the text: the files around them hold services, controllers, background jobs, records, interfaces, enums, validation, logging, and LINQ or streams over what a query already loaded. These two examples are such files, five of them each, sent as they are. The tool reads every class of a file as an entity except three kinds — a class in whose own members the code hands a query to the framework, the framework’s own API (the EF Core context), and a static class —, and a Convention or Loss record names each of them, so the split can be checked. Records, interfaces and enums are never entities. A query is every place the code hands one to the framework: a LINQ chain over a set of the context, a createQuery or createNativeQuery. Everything else — methods, constructors, the code around each query — stays where it is, and is not translated. Filter the records band to Convention to see the split.

Helpdesk: EF Core → Dapper

An ASP.NET Core helpdesk in five files: a domain file with four entity classes, an enum and a static class of state names; a context with its DbSets, a little fluent configuration and a SaveChangesAsync override that stamps and logs; a service with the records and the interface it speaks in; an API controller; and a background job with a static class of CSV helpers. Out of it come the four entities and eight queries — six in the service, one in the controller’s lookup action, one in the job, each turned into a Dapper method over its SQL. The page the service computes in code becomes OFFSET @skip ROWS FETCH NEXT @take ROWS ONLY, FirstOrDefaultAsync TOP (1), !t.Escalated t.Escalated = 0, the conditional in a sum a CASE, EF.Functions.Like with a pattern built in code LIKE @pattern, and a Contains over another set an IN subquery; the job’s context, taken from a service scope, is a context all the same. What is left alone says as much: the entities’ methods and computed properties (IsOpen, DisplayName), the Add and SaveChangesAsync calls, LINQ over lists the code has loaded (tickets.Select, overdue.Count, backlog.Sum), adding a comment to a ticket’s collection, and calls that look like a chain over a member but are not LINQ at all — Random.Shared.Next, span.TotalHours.ToString, scope.ServiceProvider.GetRequiredService. Dapper has no place for any mapping fact, so most of the records are its losses, one line per fact.

Clinic: Hibernate → EF Core

A Spring Boot clinic in five files: three entities with constants, constructors, a static factory, a lifecycle callback, a nested enum, business methods and equals; a @Service with a nested interface and two nested records, an injected EntityManager, a clock and a logger; and a @Component whose scheduled job writes a CSV. Out of it come the three entities and seven queries. Each setParameter becomes a typed parameter of the generated method, setMaxResults a Take — also before getResultStream().findFirst() —, the entity join a Join, not exists a negated Any, and the report’s grouping with its conditional count a GroupBy with a Sum over a conditional, ordered by g.Count(). The native SQL of the report is read as a query like any other. Two queries aggregate over all their rows without a grouping — the clash count and that native report —, which LINQ can say only by the call that runs the query, so they go out as native SQL through Database.SqlQuery with a row class, and three Fallback records name why. Left alone: em.find and em.persist, which hand no query over; a SQL-looking string constant used for logging; the callback, the loops and the streams. The @Email validation annotation is a Loss record, because the mapping has no place for it.

Real projects

Every example above was written for this page. The five below were not: they are excerpts of open-source projects, one for each source framework but NHibernate, taken at one commit under the project’s own licence. The files are the project’s, changed only where the tool reads a construct in another form or does not translate it at all — statements that write, code that only serves them — and every file says so in a note at its top: which project, which commit and path, and either Unchanged apart from this note or what was changed. The meaning stays the project’s: the same tables, the same rows. The excerpts and their licences live in SampleData/ThirdParty of the repository, with a README per project that lists every change. What these excerpts showed about the tool, and which other projects were considered, is in the repository’s documentation. The inputs run to dozens of files, so the panes start folded.

Keycloak: Hibernate → NHibernate

Keycloak, the identity and access management server, keeps its users, roles, groups and clients in JPA entities on Hibernate. The input is 21 of them and one class the project does not have: Keycloak runs its queries by name from @NamedQuery annotations, which the tool does not read, so KeycloakNamedQueries.java hands the 47 read-only ones to em.createQuery, one method each. Two kinds of change keep them readable, each marked where it is made. Ten entities put @Id on a @ManyToOne; there the key part is written as its own column beside a relation that does not write it. Twenty queries compare a whole entity, follow a path through an association or project one side of a join; there they compare a key column or ask a correlated exists. Out of it come 21 NHibernate classes with their mappings — ten composite keys as <composite-id> with the Equals, GetHashCode and [Serializable] NHibernate requires, the relation over each key part as a many-to-one with insert="false" — and the 47 queries in HQL, 46 of them with the LINQ form beside it: the count of the members of a set of groups has none, and an Omitted record says why. The other records name what NHibernate has no place for: the @NamedQueries still on the entities, Hibernate’s own @Fetch and @BatchSize, element collections, cascades, initializers such as KeycloakModelUtils.generateId(); a Conflict says that eleven nested key classes share the name Key. Switch the target to EF Core and that count is refused: EF Core says it only in native SQL, where it cannot bind the list of groups.

Apache Ambari: EclipseLink → EF Core

Apache Ambari, the manager of Hadoop clusters, maps its tables with EclipseLink. The input is its six alert entities, unchanged — definitions, groups, targets, the current alert, its history, the notices sent — and a class with 35 of their 41 read-only named queries handed to em.createQuery. Eight of those reach the alert’s history or definition through the key column the entity maps beside the association — a correlated EXISTS over it, or a comparison of it — instead of a path through the association; six are left out with a note, five of them because they compare a parameter with an enum attribute whose type lies outside the excerpt. EF Core receives the six classes and two junction entities for the two many-to-many relations Ambari declares with @JoinTable, a Convention record beside each, and 35 LINQ queries: each EXISTS becomes an Any over another set, the BETWEEN two comparisons. Most of the records are what EF Core’s annotations cannot say: Ambari’s TABLE generators, @Enumerated, @Lob, and the columns Ambari maps twice, once through the relation and once read-only beside it.

Chinook: Dapper → EF Core

A Web API over the Chinook music store whose author wrote the data layer twice, behind the same repository interfaces: once with Dapper, once with EF Core. JPetStore: MyBatis → Dapper
