Testing on the LDBC social network

The LDBC Social Network Benchmark is the data set and the query workload that graph and relational database systems are compared on. Here it is a second domain for the translator, and one it did not choose: 41 read queries written by somebody else, over a social network of seventeen tables. All of them the tool translates into every framework as the specification defines them; where a text has a shape the specification does not dictate — the five searches over the graph above all — this page says which shape and why, the test suite holds every one of those claims, and LDBC's own validation set judges the Interactive ones.

Data generated by the LDBC SNB Datagen, used under CC BY 4.0. This is not an LDBC Benchmark: nothing run here is an audited result, and the queries are translations of the specification's definitions, not its reference implementations. The specification is The LDBC Social Network Benchmark, version 2.2.4.

The data set

The container loads SNB Interactive v1 at scale factor 1, in the layout LDBC calls CsvMergeForeign: a file per entity with its one-to-many edges merged in as foreign-key columns, and a file per many-to-many edge. It is the part of the network the benchmark loads in bulk, 90 % of it; the update streams that replay the rest are not loaded. Interactive v1 is the workload the most systems have been measured on, and LDBC publishes validation sets for it — parameters with their expected results, interleaved with the inserts of the update stream — from scale factor 0.1 to 10. The set of the loaded scale factor is loaded beside the data, in the table ValidationOperation; the test suite replays it in order and removes its inserts again, so the data set stays as loaded.

Every edge table has a composite primary key made of its two ends, and every foreign key is declared, so the database catalog knows every relation. The tables follow the relational mapping of LDBC's own reference implementations, and depart from the files where those do:

  • Posts and comments are one table, Message, as in the PostgreSQL implementation of Interactive and the Umbra implementation of BI. A comment is a message with a ParentMessageId. The specification makes them subclasses of an abstract message, and inheritance is outside what the translator reads.
  • Every message carries the root post of its thread, the forum that contains it and its language (RootPostId, ContainerForumId, RootPostLanguage), filled when the data is loaded, as the Message table of the BI implementation does. Without them, a comment reaches its forum only by walking up the replies — recursion.
  • Friendship is stored in both directions. The files state an undirected edge once and leave it to the loader.
  • Every string compares binary, because the specification orders strings by code point; a case-insensitive collation would break ties differently.

Using it

Start the database

From the ORMConvertor directory, docker compose up --build starts the application and a SQL Server with three databases: the WideWorldImporters sample, LdbcSnb, and Fiben of the FIBEN page. The archive (222 MB) is downloaded while the image is built; the first start unpacks it and loads it, which takes a minute or two while the server already answers. The volume keeps the data, so later starts skip the load. Connect with: 

Server=localhost,1444;Database=LdbcSnb;User ID=sa;Password=Testingorms123;TrustServerCertificate=true

Another scale factor LDBC publishes for Interactive v1 — 0.1, 0.3, 3, 10 and up — is a build argument, LDBC_SCALE_FACTOR=0.1 docker compose up --build, and none leaves the data set out of the image. The example parameters below were chosen on scale factor 1.

Translate against it

The queries are written for Dapper, as plain classes and T-SQL, because the reference implementations of LDBC are SQL. A Dapper source states no key, no relation and no type of a parameter; the translator takes all of that from the database catalog, so the instance has to read LdbcSnb as its catalog: 

ORMCONVERTOR_CATALOG_DATABASE=LdbcSnb docker compose up --build

or, in PowerShell, $env:ORMCONVERTOR_CATALOG_DATABASE = "LdbcSnb" before the same command. Without it the catalog is WideWorldImporters, which has none of these tables, and most targets refuse. The line above every translation below says whether the instance read a catalog at all.

Run a query yourself

Every query below with a text has Copy as a T-SQL script: its parameters as declared variables with the example values, then the query, ready for sqlcmd or Management Studio against LdbcSnb.

What translates, and how

All queries are translated as specified: the text returns what the specification defines, and every framework receives it. The constructs the catalog needs are joins along foreign keys and along edge tables, paths of a fixed length written as IN subqueries over the walks of that length, negative edges as NOT EXISTS, grouped counts with HAVING, CASE, scalar subqueries and the first k rows, a query over the result of another, written as a common table expression or a derived table (BI 4, BI 8, BI 12, BI 13), a hierarchy of any depth as a recursive one (IC 12), results that are lists (IC 1, IC 12), grouping by an expression (BI 1), the best row of every group by a row number over a window (BI 14), arithmetic over dates (BI 17), and the shortest and cheapest paths over the graph (IC 13, IC 14, BI 15, BI 19, BI 20) as a breadth-first search written as a chain of non-recursive definitions — the two headings below say why and how deep. Where the specification adds days to a parameter, the caller passes the end of the window. Every query carries its status in the list below and in the table: a query the tool could say only after a simplification, or not at all, would be shown with that status rather than left out.

Recursion and the searches over the graph

The catalog has two kinds of recursion, and they are written differently. The hierarchy of tag classes (IC 12) is a tree, and a recursive common table expression descends it as the specification reads it. The five searches over the graph — the shortest path along knows (IC 13), every shortest path with its weight (IC 14), and the cheapest path where an edge costs what the replies between its ends, the shared universities or the forums of a timeframe make it (BI 19, BI 20, BI 15) — run over a graph with cycles, and there a recursive definition of SQL Server cannot say them: its recursive member may neither merge rows nor look at an earlier level, so it enumerates walks rather than persons. At an average degree of 39 over scale factor 1 that is 910 thousand walks three steps from the example person and 95 million at four, for 26 new persons. No data set with cycles lets such a text run unbounded, and a text bounded at a few steps misses a pair that lies further apart — it answers a simpler question than the specification asks. With the weights of BI 19 the planner also recomputes the weight definition for every key the recursion reaches, and the query does not finish in 500 s.

So the five are written as a breadth-first search in a chain of non-recursive definitions, one shape for the unweighted and the weighted searches alike. Step is every edge of the query at its cost, beside every person as its own neighbour at no cost; level 0 is the person the search starts from at no cost — for BI 19 every person of the first city at once —, and level k+1 holds, for every person, the cheapest cost over level k plus one edge — the person itself at no cost keeping what the previous level found. A level therefore holds persons, not walks, each level reads the previous one exactly once, and the work grows linearly with the edges and with the number of levels: it is Bellman–Ford, which with a unit cost is a breadth-first search. The answer is read off the last level — the second person joined to it, or the persons of the second city at the cheapest cost of all. IC 14 adds a second chain from the other end that reconstructs the paths: it extends a path only to a neighbour one step nearer to the goal, as the levels of the search say, and sums the weight once over every finished path. Dapper, MyBatis and Hibernate write the chain in their own query language and EF Core in LINQ; NHibernate and EclipseLink write it in native SQL, because a named intermediate result is what HQL of NHibernate 5.7 and JPQL do not have.

How deep a search goes

A chain of d levels reaches every person within d edges, so it is exact over a data set once d is as large as the data need — and that number is measured, not guessed. For a search by the number of steps it is the diameter of the graph, the longest of all shortest paths. For a search by cost it is the most edges a cheapest path has, the fewest among equally cheap ones, because after that many rounds every pair has its cost. Both are measured over scale factor 1 from every person, not from a sample, over the edges the query itself defines, since the edges differ from query to query:

Where the cost of an edge depends on the parameters (BI 15), the depth holds for the example timeframe and another timeframe may need another; the note of the query says so. The text of each query has exactly that many levels, and the depth stands beside the query with what it measures — the list below shows it. Three tests hold the claim: one counts the levels of the text against the stated depth; one runs the same search in its own code over the same data — Bellman–Ford to the stated depth over edges read by the test's own SQL, from the example parameters and from persons, cities and companies drawn from the data — and compares the rows; and one measures the depth of the data set from every person and asserts that it is not larger than the text's. The last holds only over the data set the catalog names, which the database records in its ldbc.dataset property; over another the test says so. A data set deeper than the text would turn the chain into a bound again: then the text grows by levels, at a linear cost, and the data are never cut down.

Over scale factor 1 the five read in 0.13 s to 6.6 s with turbo on (2026-10-15), and in the environment of the measurements — one-threaded plans, no turbo — in 0.27 s to 118 s (2026-10-17), BI 19 the longest, every level reading the definition of its weights once.

A target whose query language cannot say a query writes it in the native SQL of its database instead, through its framework's own API — SqlQuery in EF Core, CreateSQLQuery in NHibernate, createNativeQuery in JPA — and says so in a record. That is counted apart from a translation into the target's own language.

EF Core writes in native SQL: recursion and a window, which LINQ does not have, and a count over the whole result, which ends a LINQ chain instead of forming a query (BI 11). An outer join that also filters in its ON clause it writes in LINQ: the filter of the joined table before the join, or the rows of that table that meet the whole condition, row by row. NHibernate writes and EclipseLink in native SQL: the queries over the result of another or over themselves — the five path queries among them, since a level is an intermediate result —, arithmetic over dates and lists, which HQL of NHibernate 5.7 and JPQL do not have, and for EclipseLink a conversion of a type (BI 1), whose JPQL hands the Java type name to SQL Server. A list parameter in that native SQL (BI 12) the generated EclipseLink method expands itself, one placeholder per element, because the native query of EclipseLink 5.0 does not. Four queries whose outer join named an inner join (IS 7, IC 5, BI 2, BI 5) are written so that it does not — the same sentence with another root, or an existence test — because EclipseLink writes its inner joins after the outer ones; the note of each says so. Hibernate writes : a text converted into a text, which HQL 7.4 writes as varchar(max). No target refuses a query. Every other translated query reaches all five targets in their own query language.

Every query in every target

One row per query and one column per target: the target's own query language, its native SQL, or a refusal. Point at a cell for the reason a query did not stay in the target's language. The table is drawn from the same catalog as the list below, so the two cannot disagree.

QueryStatus

“Translated” holds for every query at the first level of verification: the target artifact is generated without a Failure record, the EF Core and NHibernate artifacts compile, and the Java targets compile theirs and their frameworks accept them. Whether it returns the right rows is judged for the 21 Interactive queries by LDBC's own validation set, replayed against the generated artifact of every framework: a query translated as specified has to agree with it on every read. Each query below names the operation of the validation set that judges it. Both suites replayed the whole set of scale factor 1 — 138,747 lines — on 2026-10-12 (.NET) and 2026-10-14 (Java) with every read agreeing in all six frameworks, the five path queries then in an earlier text bounded at a few steps; the present texts have so far been judged over the first 500 lines of the same set in both suites on 2026-10-18, every read agreeing in all six frameworks, and the whole set is the next run. LDBC publishes no such set for the Business Intelligence queries over this data, so their status is the author's claim, checked for the three BI path queries against a search the test runs itself. Every text below does run, against the LDBC tables, in the test suite.
