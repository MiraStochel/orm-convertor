Testing on the LDBC social network

The LDBC Social Network Benchmark is the data set and the query workload that graph and relational database systems are compared on. Here it is a second domain for the translator, and one it did not choose: 41 read queries written by somebody else, over a social network of seventeen tables. Some of them the tool translates into every framework, some only after a simplification, some not at all — this page says which, and why, and the test suite holds every one of those claims.

Data generated by the LDBC SNB Datagen, used under CC BY 4.0. This is not an LDBC Benchmark: nothing run here is an audited result, and the queries are translations of the specification's definitions, not its reference implementations. The specification is The LDBC Social Network Benchmark, version 2.2.4.

The data set

The container loads SNB Interactive v1 at scale factor 1, in the layout LDBC calls CsvMergeForeign: a file per entity with its one-to-many edges merged in as foreign-key columns, and a file per many-to-many edge. It is the part of the network the benchmark loads in bulk, 90 % of it; the update streams that replay the rest are not loaded. Interactive v1 is the workload the most systems have been measured on, and LDBC publishes validation sets for it — parameters with their expected results — from scale factor 0.1 to 10.

Every edge table has a composite primary key made of its two ends, and every foreign key is declared, so the database catalog knows every relation. The tables follow the relational mapping of LDBC's own reference implementations, and depart from the files where those do:

  • Posts and comments are one table, Message, as in the PostgreSQL implementation of Interactive and the Umbra implementation of BI. A comment is a message with a ParentMessageId. The specification makes them subclasses of an abstract message, and inheritance is outside what the translator reads.
  • Every message carries the root post of its thread, the forum that contains it and its language (RootPostId, ContainerForumId, RootPostLanguage), filled when the data is loaded, as the Message table of the BI implementation does. Without them, a comment reaches its forum only by walking up the replies — recursion.
  • Friendship is stored in both directions. The files state an undirected edge once and leave it to the loader.
  • Every string compares binary, because the specification orders strings by code point; a case-insensitive collation would break ties differently.

Using it

Start the database

From the ORMConvertor directory, docker compose up --build starts the application and a SQL Server with two databases: the WideWorldImporters sample, and LdbcSnb. The archive (222 MB) is downloaded while the image is built; the first start unpacks it and loads it, which takes a minute or two while the server already answers. The volume keeps the data, so later starts skip the load. Connect with: 

Server=localhost,1444;Database=LdbcSnb;User ID=sa;Password=Testingorms123;TrustServerCertificate=true

Another scale factor LDBC publishes for Interactive v1 — 0.1, 0.3, 3, 10 and up — is a build argument, LDBC_SCALE_FACTOR=0.1 docker compose up --build, and none leaves the data set out of the image. The example parameters below were chosen on scale factor 1.

Translate against it

The queries are written for Dapper, as plain classes and T-SQL, because the reference implementations of LDBC are SQL. A Dapper source states no key, no relation and no type of a parameter; the translator takes all of that from the database catalog, so the instance has to read LdbcSnb as its catalog: 

ORMCONVERTOR_CATALOG_DATABASE=LdbcSnb docker compose up --build

or, in PowerShell, $env:ORMCONVERTOR_CATALOG_DATABASE = "LdbcSnb" before the same command. Without it the catalog is WideWorldImporters, which has none of these tables, and most targets refuse. The line above every translation below says which catalog the instance read.

Run a query yourself

Every query below with a text has Copy as a T-SQL script: its parameters as declared variables with the example values, then the query, ready for sqlcmd or Management Studio against LdbcSnb.

What translates and what does not

as specified

The text returns what the specification defines. Joins along foreign keys and along edge tables, paths of a fixed length written as IN subqueries over the walks of that length, negative edges as NOT EXISTS, grouped counts with HAVING, CASE, scalar subqueries and the first k rows, and a query over the result of another, written as a common table expression or a derived table (BI 4, BI 8, BI 12, BI 13). Where the specification adds days to a date, the caller passes the end of the window.

simplified

The text leaves out one part and says which: results that are lists (IC 1, IC 12), arithmetic over dates (IC 7, BI 17) and keeping the best row of every group (BI 14).

not translated

Searches over the graph — shortest and cheapest paths of any length (IC 13, IC 14, BI 15, BI 19, BI 20) — have no place in a query without recursion. Grouping by an expression (BI 1) is refused as well.

EF Core refuses of the translated queries: an outer join that also filters in its ON clause, which a LINQ join cannot say, and a count over the whole result, which ends a LINQ chain instead of forming a query. NHibernate and EclipseLink refuse : the queries over the result of another, because HQL of NHibernate 5.7 and JPQL have neither WITH nor a subquery in FROM. Every other translated query reaches all five targets.

“Translated” is the first level of verification: the target artifact is generated without a Failure record. Whether it returns the rows the source returns is the differential verification, which does not run over this data set yet. Every text below does run, against the LDBC tables, in the test suite.
