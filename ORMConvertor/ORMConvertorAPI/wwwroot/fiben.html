Testing on the FIBEN finance benchmark

FIBEN is IBM Research's benchmark for asking a financial data mart questions in plain English: 300 questions over 152 tables built on the FIBO and FRO ontologies, 170 of them nested, and for each one the SQL that answers it — 237 distinct queries. Here it is the third domain for the translator, and the second it did not choose: a population of queries written by somebody else, each with its intent stated in a sentence, deep in nesting where LDBC is wide in joins. The tool does not answer questions; it translates the SQL, and this page shows how far.

FIBEN is published by IBM under the Apache License 2.0, data included: github.com/IBM/fiben-benchmark, J. Sen et al., ATHENA++: Natural Language Querying for Complex Nested SQL Queries, PVLDB 13(11), 2020. Nothing run here is a run of the benchmark: the queries are the benchmark's own SQL carried from the Db2 dialect into T-SQL, and the question beside each one is its intent, for the reader and for the comparison with language models.

The data set

The container loads the benchmark's own data into a third database, Fiben, beside WideWorldImporters and LdbcSnb: the 152 tables of FIBEN.sql with their 159 foreign keys, and the 400 MB of CSV the repository ships, 720 MB once loaded. Every primary key is one BIGINT column; most tables are FIBO or FRO concepts that hold nothing but a key and a name, and 111 of them are empty in the published data. The data set is named after the commit it was taken from.

The schema arrives in the Db2 dialect and is carried over by a small import tool (FibenImport), which also generates the Dapper entity class of every table and the catalog of queries. What changes on the way is written down in the tool and nowhere else:

  • Types follow the declarations: DOUBLE PRECISION is FLOAT, TIMESTAMP is DATETIME2(6), VARCHAR(1024) is NVARCHAR(1024) because the data holds names outside ASCII, and every text compares binary, as Db2 compares it.
  • Nothing is indexed beyond the keys, because the benchmark declares nothing beyond them. Two queries take minutes for it.
  • Names stay as the ontology spells them, LISTEDSECURITY and HASTICKERSYMBOL, uppercase and without a word boundary: the foreign convention is one of the things the catalog completion is measured against.

Using it

Start the database

From the ORMConvertor directory, docker compose up --build starts the application and a SQL Server with three databases. The benchmark's data.zip (80 MB) is downloaded while the image is built; the first start unpacks it and loads it, which takes two to three minutes while the server already answers. The volume keeps the data, so later starts skip the load. Connect with: 

Server=localhost,1444;Database=Fiben;User ID=sa;Password=Testingorms123;TrustServerCertificate=true

FIBEN_DATASET=none docker compose up --build leaves the benchmark out of the image; another commit of the repository selects its archive.

Translate against it

The queries are written for Dapper, as plain classes and T-SQL, because the benchmark's queries are SQL. A Dapper source states no key, no relation and no type; the translator takes all of that from the database catalog, so the instance has to read Fiben as its catalog: 

ORMCONVERTOR_CATALOG_DATABASE=Fiben docker compose up --build

Without it the catalog is WideWorldImporters, which has none of these tables. Every query below is sent with the entities of the tables it reads and nothing else, as the run sends it; the line above each translation says whether the instance read a catalog at all.

Run the catalog

The catalog does not run as part of a build. It runs on demand, for a version or a substantial change, in both suites one after the other, in five stages: the catalog is complete; every query reaches every target; the artifacts compile; every target returns the rows the catalog's own text returns, and the text returns the rows the frozen judge holds; and every cell is measured. The commands are in the README of the solution, the record of each run in the run records of its documentation.

What translates, and how

All queries are translated as the benchmark states them: the text states the benchmark's query, every framework receives it, and the run holds every target to its rows. The constructs the catalog needs are inner joins along foreign keys, grouped sums, averages, counts, minima and maxima with HAVING, subqueries in IN and NOT IN, correlated scalar subqueries compared with an aggregate, UNION, the first n rows, BETWEEN, YEAR and MONTH, a common table expression, derived tables nested three deep with an aggregate or a ranking over a window inside them — AVG, MAX, MIN or DENSE_RANK OVER (PARTITION BY …) —, and a subquery in the ON condition of a join. An average comes back from every target as SQL computes it: over whole numbers with the quotient cut off, over decimals as a decimal. Every query carries its status in the list below and in the table: a query the tool could say only after a simplification, or not at all, would be shown with that status rather than left out, and a text that returned less or other than the benchmark's query would say what in its note.

Nesting, by Kim's taxonomy

What makes FIBEN a test of its own is nesting: where LDBC is wide in joins, FIBEN answers a question with a query inside a query. The catalog sorts every query by Kim's taxonomy of nested SQL, by what the inner block does and whether it refers to the outer one: type N is a subquery in IN that neither aggregates nor refers outward; type A a subquery that returns one aggregate, compared with a column of the outer block; type J a subquery that refers to the outer block and does not aggregate; and type JA one that does both, an aggregate over the rows the outer block's row selects. The catalog holds single-block queries, of type N, of type A, of type J and of type JA, answering questions over of the tables; each query names its type below, and the table of every query in every target is grouped by it.

The tool reads a nested query as the tree it is. A subquery that stands where a value or a set of values stands — in IN, beside a comparison, in EXISTS — is an operand of the condition that holds it, and a condition is a tree, so a subquery may stand in WHERE, in HAVING and in the ON condition of a join alike, correlated or not. A subquery that stands where a table stands — a derived table or a common table expression — is a named intermediate result, which may hold a derived table of its own, so the three levels of the benchmark's deepest queries are three definitions, and a window inside one is a column of it like any other. Where a target's language stops short of the tree, the query goes out in native SQL, as the next paragraph says: LINQ has no form for a scalar subquery that is not a single ungrouped aggregate and queries no aggregate projected without a grouping, HQL of NHibernate 5.7 has no TOP inside a subquery, no UNION and no intermediate result — and the documented run below counts what that came to in each target.

A target whose query language cannot say a query writes it in the native SQL of its database instead, through its framework's own API, and says so in a record; that is counted apart from a translation into the target's own language. Which queries each target writes that way is not a claim of the catalog but a measure of the version, taken by the run and shown in the overview below, which the reader can fill from the running instance.

The documented run

What the run found

  • Where a target left its language. No query was refused: all 237, 131 of them nested, reached all five targets. EF Core wrote 61 of them in native SQL: 36 that project an aggregate without a grouping, which a LINQ chain can only end in, not query; 23 for a scalar subquery that is not a single ungrouped aggregate, where First() would silently pick one of several rows that SQL refuses; and 2 for an aggregate or a ranking over a window (queries 99 and 237). It stayed in LINQ for 80 of the 106 single-block queries but for only 12 of the 27 correlated queries without an aggregate (type J). NHibernate wrote 23 in native SQL: 14 for TOP inside a subquery, which HQL 5.7 cannot say, 7 for UNION and 2 for an intermediate result (99 and 237). Hibernate wrote the same 14 that way; EclipseLink 41: those 14, the 18 that open their HAVING with an aggregate over a joined entity, the 7 unions whose members join other entities and the same 2 intermediate results.
  • Two semantic differences between SQL and LINQ. SUM over no values is NULL in SQL and 0 in LINQ, because EF Core keeps the meaning of Enumerable.Sum and writes COALESCE(SUM(x), 0); and an equality of two values that may be NULL is unknown in SQL where both are, but true in LINQ, which EF Core writes as a = b OR (a IS NULL AND b IS NULL). Translated word for word, query 207 (who holds IBM stocks more than he holds Alphabet) would return besides the text's answer everyone who holds IBM and no Alphabet at all. The translation carries SQL's meaning into LINQ and back - a sum under a guard of the count of its values, an equality that holds only where the values are not NULL - and takes the value of one group by Max(), whose subquery SQL Server unnests, not by a subquery that ends in TOP(1), which it does not. Every cell of EF Core agrees with the source.
  • What the Java frameworks need. Hibernate reads join POSTALADDRESS p beside a joined entity whose column is also called POSTALADDRESS as a join of that column, so the JPQL for Hibernate names such an entity by its fully qualified class name. EclipseLink leaves the joins of a UNION member out of its SQL and answers other rows, so a set operation with a joined member goes out in native SQL for EclipseLink; and it rebuilds the HAVING on the root of the block when the clause opens with a path over another variable, so such a query goes out in native SQL too. It also trims the trailing spaces of a CHAR(5) value (query 63) - a setting of the consumer's session, which the artifact does not make, a stated limit of the target, and the one cell of the run that differs from the source.
  • The benchmark's own texts needed care. Two of the published queries do not run in any dialect (136 lacks a closing parenthesis, 172 a closing quote), four group a correlated subquery by a column of the outer query, which Db2 accepts and SQL Server refuses, one derived table has no alias, three nested derived tables share the name a, a hundred comparisons put a number in quotes against a BIGINT column, and sixteen aggregates are projected without a name. Each is a named patch or a rule of the import, and every string literal of every query is checked to equal the benchmark's.
  • Ninety-six of the 237 queries return no rows over the benchmark's own data: the questions name dates, companies and investors the published data does not hold. Thirty-four return more than a thousand rows, three more than a hundred thousand (query 32, the e-mail addresses of account holders in California with their accounts and addresses, 610 907 rows), which is why the judge keeps a digest of every result and the rows themselves only up to a thousand.
  • The frameworks cost the same, the queries do not. Summed over the catalog, the medians of the six frameworks lie between 637 s (NHibernate) and 663 s (EclipseLink). Two queries set the length of the run: 205 (which companies reported year over year revenue loss for 2019) at about 170–190 s and 233 at about 90–98 s per execution, correlated scalar subqueries with five joins evaluated for every outer row over tables without an index beyond their keys.

Every query in every target

One row per query and one column per target. The status column is the catalog's; a target column is filled by the button in its heading, which translates every query into that target through the running instance, one after another, and writes the outcome into its cell — the target's own language, native SQL, or a refusal. Point at a cell for the reason. This is the first stage of the run, watched live; whether the rows agree is the fourth, which only the run itself does.
