Testing on the FIBEN finance benchmark

FIBEN is IBM Research's benchmark for asking a financial data mart questions in plain English: 300 questions over 152 tables built on the FIBO and FRO ontologies, and for each one the SQL that answers it — 237 distinct queries, 170 of them nested. Here it is the third domain for the translator, and the second it did not choose: a population of queries written by somebody else, each with its intent stated in a sentence, deep in nesting where LDBC is wide in joins. The tool does not answer questions; it translates the SQL, and this page shows how far.

FIBEN is published by IBM under the Apache License 2.0, data included: github.com/IBM/fiben-benchmark, J. Sen et al., ATHENA++: Natural Language Querying for Complex Nested SQL Queries, PVLDB 13(11), 2020. Nothing run here is a run of the benchmark: the queries are the benchmark's own SQL carried from the Db2 dialect into T-SQL, and the question beside each one is its intent, for the reader and for the comparison with language models.

The data set

The container loads the benchmark's own data into a third database, Fiben, beside WideWorldImporters and LdbcSnb: the 152 tables of FIBEN.sql with their 159 foreign keys, and the 400 MB of CSV the repository ships, 720 MB once loaded. Every primary key is one BIGINT column; most tables are FIBO or FRO concepts that hold nothing but a key and a name, and 111 of them are empty in the published data. The data set is named after the commit it was taken from.

The schema arrives in the Db2 dialect and is carried over by a small import tool (FibenImport), which also generates the Dapper entity class of every table and the catalog of queries. What changes on the way is written down in the tool and nowhere else:

  • Types follow the declarations: DOUBLE PRECISION is FLOAT, TIMESTAMP is DATETIME2(6), VARCHAR(1024) is NVARCHAR(1024) because the data holds names outside ASCII, and every text compares binary, as Db2 compares it.
  • Nothing is indexed beyond the keys, because the benchmark declares nothing beyond them. Two queries take minutes for it.
  • Names stay as the ontology spells them, LISTEDSECURITY and HASTICKERSYMBOL, uppercase and without a word boundary: the foreign convention is one of the things the catalog completion is measured against.

Using it

Start the database

From the ORMConvertor directory, docker compose up --build starts the application and a SQL Server with three databases. The benchmark's data.zip (80 MB) is downloaded while the image is built; the first start unpacks it and loads it, which takes two to three minutes while the server already answers. The volume keeps the data, so later starts skip the load. Connect with: 

Server=localhost,1444;Database=Fiben;User ID=sa;Password=Testingorms123;TrustServerCertificate=true

FIBEN_DATASET=none docker compose up --build leaves the benchmark out of the image; another commit of the repository selects its archive.

Translate against it

The queries are written for Dapper, as plain classes and T-SQL, because the benchmark's queries are SQL. A Dapper source states no key, no relation and no type; the translator takes all of that from the database catalog, so the instance has to read Fiben as its catalog: 

ORMCONVERTOR_CATALOG_DATABASE=Fiben docker compose up --build

Without it the catalog is WideWorldImporters, which has none of these tables. Every query below is sent with the entities of the tables it reads and nothing else, as the run sends it; the line above each translation says whether the instance read a catalog at all.

Run the catalog

The catalog does not run as part of a build. It runs on demand, for a version or a substantial change, in both suites one after the other, in five stages: the catalog is complete; every query reaches every target; the artifacts compile; every target returns the rows the catalog's own text returns, and the text returns the rows the frozen judge holds; and every cell is measured. The commands and the record of each run are in the README of the solution.

What translates and what does not

as the benchmark states them

The text states the benchmark's query, and the run holds every target to it. Inner joins along foreign keys, grouped sums, averages, counts, minima and maxima with HAVING, subqueries in IN and NOT IN, correlated scalar subqueries compared with an aggregate, UNION, the first n rows, BETWEEN, YEAR and MONTH, and a common table expression.

simplified

The text returns less or other than the benchmark's query and its note says what.

not translated

Two shapes the representation does not carry, each refused in every target with its reason in the note: an aggregate over a window — AVG, MAX or MIN OVER (PARTITION BY …) — inside a derived table, where it is a column the query around it reads; and a scalar subquery inside the ON condition of a LEFT JOIN.

By Kim's taxonomy the catalog holds single-block queries, of type N, of type A, of type J and of type JA, answering questions over of the tables.

A target whose query language cannot say a query writes it in the native SQL of its database instead, through its framework's own API, and says so in a record; that is counted apart from a translation into the target's own language. Which queries each target writes that way is not a claim of the catalog but a measure of the version, taken by the run and shown in the overview below, which the reader can fill from the running instance.

The first documented run

On 2026-10-18 the catalog ran for the first time in both suites, one after the other, against the container's Fiben database in the fixed environment of the measurements (four processors, the server on two of them and the clients on the other two, one-threaded plans, turbo on). The .NET suite took 112 minutes for the 237 queries in Dapper, EF Core and NHibernate; the judge was made from the rows the catalog's own text returned in it. What the run found

  • Eight queries the tool refuses, in every target and for two reasons only: an aggregate over a window inside a derived table (queries 99 and 237) and a scalar subquery inside the ON condition of a LEFT JOIN (124–126, 200–202). Everything else — 229 queries, 124 of them nested — the tool translates into all five targets.
  • Where a target leaves its language. EF Core writes 59 queries in native SQL: 36 for an aggregation LINQ does not form, such as an aggregate compared with a subquery in HAVING or an average over a BIGINT, and 23 for a scalar subquery with its own joins as a comparison operand. It stays in LINQ for 80 of the 106 single-block queries but for only 9 of the 27 correlated queries without an aggregate (type J). NHibernate writes 21 in native SQL: 14 for TOP inside a subquery, which HQL 5.7 cannot say, and 7 for UNION.
  • One semantic difference between SQL and LINQ. SUM over an empty set is NULL in SQL and 0 in LINQ, because EF Core keeps the meaning of Enumerable.Sum and writes COALESCE(SUM(x), 0). A query of type JA that compares a sum with the sum of a correlated subquery therefore keeps rows in EF Core that SQL drops: query 207 (who holds IBM stocks more than he holds Alphabet) returns one person from the text, from Dapper and from NHibernate, and 211 from EF Core — everyone who holds IBM and no Alphabet at all. Five queries differ this way (150, 155, 207, 211, 213) - the only cells of the .NET run where a target disagrees with the source. A query that returns other rows than its source is a defect of the translation, open as one, and not a fix in the comparison.
  • Three things the Java frameworks taught the tool. Hibernate reads join POSTALADDRESS p beside a joined entity whose column is also called POSTALADDRESS as a join of that column, so the JPQL for Hibernate now names such an entity by its fully qualified class name (nine queries ran after the fix). EclipseLink leaves the joins of a UNION member out of its SQL and answered 49 870 rows where the text answers 189, so a set operation with a joined member goes out in native SQL for EclipseLink (four queries). And EclipseLink refuses an aggregate in HAVING over a column of an entity it joined (Invalid query key, eighteen cells): measured afterwards, it rebuilds the HAVING on the root of the block when the clause opens with a path over another variable, so such a query now goes out in native SQL. It also trims the trailing spaces of a CHAR(5) value (query 63) - a setting of the consumer's session, which the artifact does not make, and a stated limit of the target.
  • The benchmark's own texts needed care. Two of the published queries do not run in any dialect (136 lacks a closing parenthesis, 172 a closing quote), four group a correlated subquery by a column of the outer query, which Db2 accepts and SQL Server refuses, one derived table has no alias, three nested derived tables share the name a, a hundred comparisons put a number in quotes against a BIGINT column, and sixteen aggregates are projected without a name. Each is a named patch or a rule of the import, and every string literal of every query is checked to equal the benchmark's.
  • Ninety-five of the 229 translated queries return no rows over the benchmark's own data: the questions name dates, companies and investors the published data does not hold. Thirty return more than a thousand rows, three more than a hundred thousand (query 32, the e-mail addresses of account holders in California with their accounts and addresses, 610 907 rows), which is why the judge keeps a digest of every result and the rows themselves only up to a thousand.
  • The frameworks cost the same, the queries do not. Summed over the catalog, the medians of the three .NET frameworks are within two percent of each other (323–329 s). Two queries set the length of the run: 205 (which companies reported year over year revenue loss for 2019) at 182 s and 233 at 97 s per execution, correlated scalar subqueries with five joins evaluated for every outer row over tables without an index beyond their keys. Most queries run in under 50 ms. Where the frameworks differ, EF Core's SQL does: queries 120 and 121 run fifteen times faster in EF Core than from the text (its rewritten subquery gets another plan), 164 and 181 four to five times slower.
  • The catalog completion scales. Reading the catalog of 152 tables and 159 foreign keys for the first query took 408 ms; translating a query with the entities of its tables takes a few milliseconds after that, and compiling an artifact 15–30 ms.

Every query in every target

One row per query and one column per target. The status column is the catalog's; a target column is filled by the button in its heading, which translates every query into that target through the running instance, one after another, and writes the outcome into its cell — the target's own language, native SQL, or a refusal. Point at a cell for the reason. This is the first stage of the run, watched live; whether the rows agree is the fourth, which only the run itself does.
