Testing on the queries of the Stack Exchange Data Explorer

SEDE is a set of queries written by the users of the Stack Exchange Data Explorer, each with the title its author gave it: T-SQL against SQL Server, as people write it, over the application schema of a site — LIKE, TOP, CASE, window functions, common table expressions, outer joins, and everything else they allowed themselves. Here it is the fourth domain for the translator and the first whose text was never ours: human-reviewed queries of the validation and the test part of the set, run over the data of dba.stackexchange.com. The tool does not answer titles; it translates the SQL, and this page shows how far.

The queries are the validation and the test part of SEDE (M. Hazoom, V. Malik, B. Bogin, Text-to-SQL in the Wild: A Naturally-Occurring Dataset Based on Stack Exchange Data, NLP4Prog 2021), published under the Apache License 2.0 at github.com/hirupert/sede. The data are the public data dump of dba.stackexchange.com of 2024-04-06, as Stack Exchange uploaded it to the archive.org item stackexchange, under CC BY-SA 4.0, content by the users of the site. Nothing run here is a run of SEDE or a text-to-SQL task: the queries are the authors' own T-SQL with the placeholders of the Data Explorer turned into parameters, and the title beside each one is its intent, for the reader and for the comparison with language models.

The data set

The container loads the dump of one site into a fourth database, Sede, beside WideWorldImporters, LdbcSnb and Fiben: the 29 tables of the Data Explorer's schema, named and typed as SEDE names and types them, with the 38 foreign keys the official schema documentation links — Stack Exchange declares them nowhere else, and the translator reads relations from declarations. Eight tables come from the dump (Posts, Users, Comments, Votes, Badges, PostHistory, PostLinks, Tags), PostTags is derived from the tags of the questions as SEDE derives it, the type tables are filled from the documentation, and the tables the dump does not carry — review tasks, suggested edits, pending flags, post notices — stay empty. The data set is named after the site and the date of the dump.

The site is dba.stackexchange.com for three reasons: its archive fits a SQL Server Express with room to spare where Stack Overflow's would not, its subject is close to what the users of the Data Explorer ask about, and an independent benchmark chose the same site as its gigabyte-scale data. A query written for Stack Overflow returns other rows here, often none; the catalog says which, and the documented run records the share.

The schema and the queries arrive through a small import tool (SedeImport), which also generates the Dapper entity class of every table. What it changes is one thing: the placeholders of the Data Explorer become parameters. ##UserId##, ##Tag:string## and ##Limit:int?100## become @UserId, @Tag and @Limit; inside a string literal, where the Data Explorer pastes the value into the text, the literal becomes a concatenation. A parameter takes the default its author gave it, or a value chosen once over the data for the name the author used. The rest of the text is the author's, mistakes included.

Using it

Start the database

From the ORMConvertor directory, docker compose up --build starts the application and a SQL Server with four databases. The archive of the dump (305 MB) is downloaded while the image is built and checked against the checksum the archive.org item publishes; the first start unpacks it table by table, turns the XML into CSV and loads it, which takes a few minutes while the server already answers. The volume keeps the data, so later starts skip the load. Connect with: 

Server=localhost,1444;Database=Sede;User ID=sa;Password=Testingorms123;TrustServerCertificate=true

SEDE_DATASET=none docker compose up --build leaves the data out of the image; another site and date of the dump, with the address and the checksum of its archive, selects another one.

Translate against it

The queries are written for Dapper, as plain classes and T-SQL, because that is what they are. A Dapper source states no key, no relation and no type; the translator takes all of that from the database catalog, so the instance has to read Sede as its catalog: 

ORMCONVERTOR_CATALOG_DATABASE=Sede docker compose up --build

Without it the catalog is WideWorldImporters, which has none of these tables. Every query below is sent with the entities of the tables it reads and nothing else, as the run sends it; the line above each translation says whether the instance read a catalog at all.

Run the catalog

The catalog does not run as part of a build. It runs on demand, for a version or a substantial change, in both suites one after the other, in the stages of the FIBEN run: the catalog is complete; every query reaches every target; the artifacts compile; every target returns the rows the catalog's own text returns with the stated values, and the text returns the rows the frozen judge holds; and every cell is measured. The commands are in the README of the solution, the record of each run in the run records of its documentation.

What translates, and what does not

The catalog carries every query of the two parts and leaves none out. stand as the author wrote them: one valid read over the schema, which every framework receives and the run holds every target to. are not translated, each with the reason in its note: a script rather than one read (a DECLARE before the query, several statements, a temporary table), a text that does not parse or is not valid over the schema (the authors' mistakes, or a table SEDE has and the schema does not), a text that fails over the data with its values, or a result no typed target can carry, because a column of it has no name or two share one. The status is the catalog's claim and says nothing about a target: which target carries a query in its own language, which writes it in native SQL and which refuses it is the measure of a version, taken by the run and shown in the overview below, which the reader can fill from the running instance.

Of the queries, are the validation part and the test part of the set, take parameters, and together they read of the tables. What the set brings that LDBC and FIBEN do not is the language of application code against SQL Server: LIKE over bodies and tags, TOP with and without a determining order, CASE, window functions, common table expressions, outer joins, DISTINCT, date arithmetic, string functions, results whose columns are named as the Data Explorer displays them ([User Link], [Post Link]) — and the result column names that are not identifiers in C# are the one thing a LINQ target cannot take, which the catalog shows in its real extent.

A target whose query language cannot say a query writes it in the native SQL of its database instead, through its framework's own API, and says so in a record; that is counted apart from a translation into the target's own language.

The documented run

The catalog has not been run in the fixed environment of the measurements yet. The first documented run makes the judge of the catalog from the rows the catalog's own texts return, records the share of queries that return no rows over this site's data, and gives the table of every framework its numbers; until then this section says so, and the overview below is what the reader can fill from the running instance.

Every query in every target

One row per query and one column per target. The status column is the catalog's; a target column is filled by the button in its heading, which translates every query into that target through the running instance, one after another, and writes the outcome into its cell — the target's own language, native SQL, or a refusal. Point at a cell for the reason. This is the first stage of the run, watched live; whether the rows agree is the fourth, which only the run itself does.
