Tutorial

One translation from start to finish, in the five steps of the Translation screen: a small Dapper project moves to EF Core. Each step says what to do there and what you will see. The example on this page is live — its files come from this instance and step 4 really converts them — so what you read below is what the tool returns, not a picture of it. About five minutes.

1 Start from an example

Do
In Start from an example, pick A source that states little (Dapper → EF Core, 3 files) and press Load example.
See
The direction switches to Dapper → EF Core and the example's files appear as units under Input files.

The step is optional — with your own project you start at step 2. The list offers two kinds of example: the same customer written in each of the six frameworks (any target), and the examples the Examples page explains, each with the direction it is explained for. This one is the most common migration the tool is built for: a Dapper source states little — a plain class and a T‑SQL query, no key, no table, no column type — so the result shows best where the facts the target needs come from.

Open the translator with this example selected It only selects the example in the list; loading stays your click, and the translator asks before it replaces work you have there.

2 Direction

Do
Check the row source → target: Dapper on the left, Entity Framework Core on the right. Leave the source SQL dialect as it is.
See
Under Input files, the line Dapper input is read as: C#, SQL query.

Any of the six frameworks can be the source and any the target; the ⇄ button between them swaps the direction. The source decides which languages a unit may be in — that is the line above. The dialect matters only for literal SQL written for a database other than SQL Server: declare “another system” and the tool refuses that SQL instead of reading it as T‑SQL.

3 Input files

Do
Look over the units the example loaded — or bring your own with Add files or a ZIP….
See
One unit per file: a name, a language, and an editor with line numbers. These are the example's files, as this instance hands them out:

Loading the example…

A unit is a whole source file — an entity, the code that queries it, or both. The language comes from the extension (.cs, .java, .xml, .sql, .hql, .jpql). A ZIP of a project is unpacked in the browser: every file the source reads becomes a unit, the rest is listed with the reason it was left out. Add empty unit gives an editor to paste into, Remove and Clear take units away. What you type stays in this browser, so a reload loses nothing.

4 Convert

Do
Press Convert — here, or on the Translation screen (Ctrl+Enter works there too).
See
The button is busy for the moment the call takes, then a strip under it counts the artifacts and the records by kind; a badge jumps to the records.

Before sending, the screen checks what it can: no units, an empty unit, a language the source does not read, malformed XML. A syntax error in C#, Java or SQL comes back from the server as a Failure record with its line and column; the screen marks the line in the unit's editor and go to line selects it. A failure in one entity or query does not stop the rest — everything else is translated.

5 Read the result

Press Convert in step 4 and the result of the example appears here, exactly as the Translation screen shows it.

5a · The run

The header of the result states the run: both frameworks with the versions the output is written for, whether the source declared a SQL dialect, the state of the database catalog, the tool version and the run's id.

ORMConvertor run

5b · What you sent, what came back

Input on the left, output on the right. Each artifact says which units it came from and each unit which artifacts it went into — that pairing is the server's, not guessed from names. Click a name to jump to the other side. Every panel has Copy and Download.

5c · Facts

Every mapping fact the conversion held — a table, a column, a key, a type, a relation — with its origin (the source stated it, the catalog supplied it, the tool derived it) and its outcome (carried into the artifact, dropped, or not generated because the entity failed). Point at a row and the fact lights up in the panels above. The badges filter the table.

5d · Records

Everything the conversion had to decide, drop or fill in, one row each — never silently. Read Failure first: it means an artifact is missing. The legend under the badges says what each kind present means; a badge filters the table, and the Artifact column jumps to the panel the record is about.

5e · Take it with you

On the Translation screen, Download all as ZIP packs every artifact under its file name. The output is source code to put into your project; what is the project’s own stays yours to add — for EF Core the project file, the connection string and the registration of the context.

✓ Now with your own project

  1. Pick the direction first — it decides which files a ZIP contributes.
  2. Add files or a ZIP… with your entities, mappings and the code that queries them.
  3. Convert, then read Failure records first, then the facts that were not carried.
  4. Download all as ZIP.
