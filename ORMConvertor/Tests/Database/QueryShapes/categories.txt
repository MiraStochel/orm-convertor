# The query categories of requirement T2: one section per category, one line per source
# framework that can state it, naming the query units of that source relative to this
# directory. Entity units stand nowhere here - the domain of five entities under
# entities/ is the same for every category and each suite adds it itself. A source absent
# from a section cannot state the category in its language; the absence is the statement,
# and the comment above the section says why.
#
# Read by both suites from this one file, the way the differential matrix.txt is read
# (decisions 076 and 089): the .NET matrices (Tests/Combined/QueryShapeMatrixTest.cs) run
# every category dry through every direction and assert the target's text, the Java suite
# (JavaTests, shapes/QueryCategoryTest) has each Java framework compile and judge what the
# tool makes of the very same texts. The format is deliberately poorer than JSON: two
# parsers in two languages have to agree about it, and a line of "key = value" cannot be
# read two ways.
#
#   <Framework>     the query units of that source framework, in the order they are sent,
#                   entity units excluded. A MyBatis row with parameters lists the mapper
#                   interface before the document, because the interface is where MyBatis
#                   keeps the type of a parameter (decision 084). The language of a unit
#                   follows its extension, with the table matrix.txt uses.
#   refusedBy       targets whose descriptor cannot express the category, as
#                   Target:Feature - both suites expect a record naming the feature there
#                   and no query artifact (decision 053).
#   refusedFrom     sources that can write the category but whose reading the tool refuses
#                   by a stated rule, as Source:Feature - a parameter of a Dapper source has
#                   no mapping to take its scalar from without a catalog (decision 083).
#
# The domain has the shape of the shared fixture schema (TestSchema.sql): customers, orders
# under a two-part key, order lines under a three-part key whose leading parts are a
# multi-column foreign key, allocations under a four-part key, and products - so the joins
# here run over two and three columns, which is what makes the join category worth
# measuring. It has read-only data of its own, FixtureData.sql beside this file, which both
# suites create in their schema right after the fixture's own tables (decision 089): the
# differential matrix measures every category here at the fourth level. Every file here
# writes that schema as {{schema}}, and both suites substitute it - the .NET matrices read
# the texts dry with the same substitution the run against the database uses. The five
# entities carry the prefix Shop, and every source names their tables by the plural -
# ShopOrders from ShopOrder -, which is what the singular-plural rule of decision 050
# derives from the class for the two sources that state no table (Dapper, MyBatis); the
# prefix keeps those tables apart from the fixture schema's Customers, OrderLines and
# Products, because a table found under two names is a match the catalog refuses to guess
# at. Every section names its query "find" plus the category, so a MyBatis statement and
# its interface are found by the name alone.
