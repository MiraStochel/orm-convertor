# ORMConvertor

A tool for translating entities, mappings, and queries between .NET ORM frameworks (Dapper, NHibernate, EF Core) — and, in the Java ecosystem, Hibernate, EclipseLink and MyBatis — through a framework-agnostic intermediate representation, with a performance-aware advisor that recommends the best framework (or combination of frameworks) for a given query workload using ILP optimization over real benchmark measurements.

This repository continues the development of a prototype originally created by Milan Abrahám as part of his master thesis (see [Origin and attribution](#origin-and-attribution)). The fork has completed and extended the tool well beyond the original prototype — see [What the tool does](#what-the-tool-does) and [Beyond this version](#beyond-this-version).

## What the tool does

- **Entity and mapping translation** between Dapper, NHibernate, and EF Core, in any direction, including composite primary keys, multi-column foreign keys, and many-to-many relationships generated as explicit junction entities. Parsers read framework-specific source code (C# via Roslyn, NHibernate XML via LINQ to XML) into a shared intermediate representation; builders generate code for the target framework from it. Hibernate joins the matrix as the first Java framework, EclipseLink as the second and MyBatis as the third (Java entities with `jakarta.persistence` annotations, `orm.xml`, and JPQL, read and written by wrappers in C# with no JVM in the translation path; both are thin profiles over one shared Jakarta Persistence layer, and what differs between them is the defaults behind the same annotations — `AUTO` is a sequence for one and a counter table for the other, and only one of them has an annotation for national character data). MyBatis stands on neither of those layers, because it implements no specification: its wrapper is built over two layers of *language* — Java for the entity, T-SQL for the query — and it is the first framework whose mapping belongs to a statement rather than to a class, so a `<resultMap>` is read as pairs of column and property while its `<id>` is read as the identity of a result row and not as a primary key. All three are covered by the guarantees below; the rest of the Java ecosystem is not.
- **Query translation in all thirty-six directions** the six frameworks yield (LINQ is read for EF Core and NHibernate, bare HQL for NHibernate as a second source language, SQL for Dapper, JPQL for Hibernate and EclipseLink, and the mapper document for MyBatis; each target writes its own language — EF Core LINQ, NHibernate HQL, Dapper and MyBatis SQL, Hibernate and EclipseLink JPQL — so NHibernate → NHibernate round-trips textually over the bare HQL artifact). Every direction produces a query artifact and none drops a query in silence; the individual categories are not all measured across the whole matrix, and where they are not is stated in [`docs/traceability.md`](docs/traceability.md) under T2. The categories are projection (`DISTINCT` included), filtering (`IN` over a list of values included), joins, aggregation, ordering, paging, subqueries in conditions — `IN (SELECT …)`, `EXISTS`, and scalar-aggregate comparisons — and set operations — UNION, UNION ALL, INTERSECT, and EXCEPT. A shape the target cannot render faithfully refuses the artifact with a diagnostic record instead of approximating: HQL has no set operations, pagination that cannot be carried is never dropped silently, and a query that would return a different set of rows is not emitted at all — on the reading side too: a filter, join, source, or grouping a parser cannot read refuses the artifact instead of being dropped. Query parameters are carried and translated: `@id`, `:id`, `?1`, a value captured from C# and a collection bound to `IN` all arrive as one operand shape, each target writes its own placeholder together with a typed parameter of the generated method and its binding, and a positional parameter stays positional only in JPQL. What cannot be typed is refused rather than guessed: the parameter's scalar is derived from the other side of the comparison through the mapping, so a comparison that types nothing refuses the artifact. A row count of the paging is a parameter too, typed `Int` by the clause it stands in rather than by a comparison, and it reaches the query text as a placeholder or the query object as an argument, whichever the target uses. One limit is stated rather than hidden — a parameter among the values of an `IN` list is still refused.
- **Completion from the database catalog**: mapping facts the source does not state (typical for micro-ORMs like Dapper) are completed from the metadata of a connected database — columns and types, primary and foreign keys, junction tables — and every supplied fact is reported in the conversion diagnostics.
- **Structured diagnostics** for every conversion: facts the target cannot express, applied conventions, conflicts between sources, and incomplete input are returned as records alongside the generated artifacts, never lost silently.
- **Advisor**: given a set of entities and queries, translates the queries into candidate frameworks, compiles and benchmarks them against a live database (Roslyn dynamic compilation), and solves an ILP model (GLPK) to recommend a framework assignment under user constraints (framework count limit, memory budget, query weights). Currently supports Dapper and EF Core, and sits outside the guarantees below.

## Guarantees

This section is the authoritative statement of the boundary between what the tool vouches for and what merely ships in the repository, as it stands on `main`; a release freezes it together with the version number in `ORMConvertor/Directory.Build.props`, so a tag carries the boundary as it stood for that version. [`docs/architecture.md`](docs/architecture.md) §9 carries the same boundary in Czech together with the reasoning behind it, and is corrected against this section if the two ever differ.

**Covered:** entity, mapping, and query translation as described above, Hibernate, EclipseLink and MyBatis included, translation across the ecosystem boundary in both directions, a Java test suite that compiles the generated code and runs it against a real database, differential verification that runs both halves of a translated query and compares the rows against one canonical answer recorded in the repository, merging of multi-file input into one conversion with per-file input and output, completion from the database catalog, structured diagnostics of every conversion — stamped with a run identifier and the versions of the tool and of both frameworks — deterministic output, translation artifacts that never carry database credentials, translation performance measured against a stated limit, an architecture in which a new framework is a new self-contained wrapper, a web interface that takes a translation from input to result in at most five steps and reports each reading error against the unit it came from, and a documented container configuration that both runs the system and reproduces both test suites, .NET and Java, on a machine with nothing installed but Docker.

Six of those hold in a narrower sense than the words alone suggest:

- Hibernate, EclipseLink and MyBatis are covered as three frameworks, not as the Java ecosystem. Generated artifacts for each are compiled with `javac`, accepted by that framework and run against SQL Server by the Java test suite, in three source directions apiece; another Java ORM is not. A Java target enters the guarantees only once its artifacts have really been compiled and accepted in the pinned environment, which is not a formality: that run refuted one assumption about Hibernate, corrected three about EclipseLink, for MyBatis it is the framework itself that refuses a project stating one statement twice — the finding the reading side is built on — and for the suite as a whole it caught a test image that was missing files the build declares it reads, while a checkout had them all along. One thing is not claimed for MyBatis: a **dynamic statement** is not translated. A `<select>` carrying `<if>`, `<choose>` or `<bind>` is a family of statements whose members return different sets of rows, and no single member stands for the rest, so such a query is refused with a record naming the tag rather than translated into one of its members; a `<foreach>` in the canonical form is the exception, because it is a collection parameter. One thing is not claimed for EclipseLink either — lazy loading of a reference: `fetch = LAZY` on a `@ManyToOne` or `@OneToOne` is silently eager there unless the consumer project weaves its bytecode, and the intermediate representation carries no loading strategy, so the generated artifact does not state one and a source that did gets a record.
- A diagnostic record born from reading one input unit points at that unit — by the name the client sent with it, or by its position in the request. Records from the completion and generation phases name the entity and property instead, deliberately: an entity may legitimately be declared by several units, so a record about the merged entity belongs to no single file. Displaying the intermediate representation is not claimed.
- Syntactic correctness of generated files is proven by the test suite, not at run time: the translation path never compiles foreign code, and what every conversion does check is the completeness of the intermediate representation.
- Client-side validation is a helper, not a gate — it catches empty and mistyped input and malformed XML, while the server is what decides. Since 21 September 2026 a text no reader can read comes back, in every input language alike, as a record about that one unit rather than as a failed request, and it carries the line and column where the reading stopped: for SQL, Java, HQL, JPQL and XML. C# is the exception — Roslyn knows the position and the parser does not ask it for one, so a broken C# unit gets only the general record saying that nothing came of it.
- Differential verification compares against one canonical answer recorded in the repository, and the scale of that comparison is stated rather than offered as a setting: decimal places and significant digits are chosen per query, while a null is always the bare word `NULL`. Nothing is ambiguous about it — a string is rendered in quotes, so the text "NULL" and a null value differ — but two suites in two languages have to agree on one canonical form, so that one rule is fixed.
- The container configuration covers what the repository contains: the system, the database, the .NET test project, the Java test project and the instance of the tool the Java suite translates against, not the experimental pipeline, which does not exist.

**Exempt from guarantees:** four areas, each excluded as a whole rather than case by case — the Advisor and its benchmarking infrastructure (untested; the native ILP library builds only inside Docker); inheritance, components, `<join>`, and everything else beyond a flat class in NHibernate mappings, `<natural-id>`, `<idbag>` and `<array>` among them — since 21 September 2026 a hierarchy stated in an entity class is reported as well, in both ecosystems, so a class deriving from another entity of the conversion — which EF Core maps as table per hierarchy by convention and JPA by its default strategy, neither of them needing a word in the source to do it — no longer passes in silence, and a Java mapped superclass says in its own record that the class is not an entity and that the entities extending it do not receive the attributes it declares; what inheritance should mean for the intermediate representation stays exempt either way; database dialects other than SQL Server 2022 — which the tool now states rather than assumes, and on both sides of a conversion: every target framework's descriptor declares the dialect its artifacts are written for, every run record reports it, a claim the target's own type vocabulary cannot carry is written as that dialect's literal column type, and a source may declare the dialect of its own literal SQL, whereupon a declaration of another system stops that reading instead of guessing at it — the query is not emitted, the literal column type is not read, and both are reported. Mapping facts from a connected catalog are the one thing such a source still receives, because a catalog is a live schema rather than text to be interpreted; the run then says once that they came from a system the source disowned — and with the dialect also `CHECK` constraints and column defaults, whose content is a literal SQL expression the intermediate representation does not carry (unique constraints do not belong here: they are carried and written by both annotation targets); and the experimental part of the assignment, which this version does not claim at all, because the experimental pipeline does not exist. Since 21 September 2026 that is all this area still holds: cross-ecosystem translation, the Java test suite and differential verification of query results left it that day, when both suites ran green in the pinned environment, neither failing nor skipping a test — how many tests that was, and over which commit, is recorded in [`ORMConvertor/README.md`](ORMConvertor/README.md#how-large-the-suite-is-and-what-it-covers) rather than repeated here, because a count repeated in five places went stale in five places at once. The Java suite also states how large it is itself: it marks which of its tests reach the database and refuses to build if too few do, so the size the requirement asks for cannot quietly go stale in a document. Exempt is not the same as absent: such an area may well ship in the repository and run, the version simply promises nothing about it, and input that touches one is reported in the conversion records rather than silently degraded.

The remaining work is tracked in [`docs/open-items.md`](docs/open-items.md).

## Versioning and releases

Version numbers say **what the tool can do**, not what breaks if you upgrade ([decision 069](docs/decisions/069-major-marks-a-milestone-not-a-break.md)). That is a deliberate departure from ordinary semantic versioning, and it rests on a condition stated plainly: the tool is not published — no package in any registry, no released artifact besides the git tag, no consumer outside this repository. A promise not to break a consumer needs a consumer to make it to, and until there is one the number is better spent on the question that can be answered.

- **MAJOR** — the tool crosses a milestone of the assignment: a whole new ecosystem (the three Java ORMs together with cross-ecosystem translation), or the Advisor working across all supported frameworks together with the experimental part. The next one is 2.0.0, for the Java ecosystem; its condition has been met on `main` since 21 September 2026, and the release itself is still to be made.
- **MINOR** — a capability arrives within a milestone: another query category, another kind of diagnostic record, another endpoint, or an area entering the guarantee boundary.
- **PATCH** — a fix, and equally any change of the public surface that brings no new capability with it: the same input yielding a differently shaped artifact, a field leaving the REST contract, an error body changing shape. A release carries the highest position any of its changes moved, so these ride along inside a MINOR release rather than being issued on their own.

What a break gets instead of a digit is the first paragraph of the release notes. The three surfaces a release describes are unchanged — the shape of the generated artifact, the REST contract, and the guarantee boundary above — and the notes describe them in that order, output shape first. **Should the tool ever be published, this policy is replaced rather than reinterpreted**: a consumer is exactly the addressee semantic versioning is written for.

A release is an annotated tag on the commit that already carries the released number in `ORMConvertor/Directory.Build.props`, and the release notes live in the tag's annotation (`git tag -n99`) rather than in a changelog file. Tags are never moved and numbers are never reused: a release that turns out wrong is corrected by the next number. Pinned dependency versions move for exactly two reasons — a published advisory or the needs of ongoing work — and CI checks the first of those on every run and once a week.

The tag `1.0` predates this policy, uses a two-part number this policy would not issue, and does not contain the container configuration described above. Its own guarantees section is consistent about that — it lists containerized deployment among the areas it exempts. What briefly claimed the configuration was the working `README.md` on `main`, whose heading still read *Version 1.0 guarantees* after its body had already moved on; that mismatch is what prompted the policy. Under the rule just stated the tag is not moved: the release `1.1.0` corrects the situation instead, and is a MINOR step for a single reason — an area entered the boundary above, while the generated artifacts and the REST contract are unchanged.

The release `1.2.0` closes the first milestone: entity, mapping, and query translation across the three .NET frameworks — which is what everything above described at the time, before the Java ecosystem joined it. It is MINOR for two reasons at once — capabilities arrived inside the milestone, and two whole areas left the boundary above, subqueries and the textual NHibernate → NHibernate round-trip, leaving the four that remain. The changes of artifact shape and the new error body ride along inside it as PATCH; each of them is named in the first paragraph of that tag's annotation, which is where to look before upgrading a consumer built against an older one.

## Getting started

The tool lives in the `ORMConvertor` directory. In short:

```sh
dotnet run --configuration Release --launch-profile http --project ORMConvertorAPI/ORMConvertorAPI.csproj
```

then open `http://localhost:5072/orm/`. The frontend is served as-is from `ORMConvertorAPI/wwwroot` — there is nothing to compile. On a machine with Docker, `docker compose up --build` from `ORMConvertor/` starts the application together with a SQL Server holding the sample database, and the pair `docker compose --profile test build tests` followed by `docker compose --profile test run --rm tests` runs the whole test suite without a .NET SDK or a database of your own. The `build` half is not decoration: `run` on its own reuses whatever image is already there, so over a changed tree it measures the tree that image was built from — which has silently reported a stale suite twice (see [`ORMConvertor/README.md`](ORMConvertor/README.md#tests)). For prerequisites and details, see [`ORMConvertor/README.md`](ORMConvertor/README.md).

## Benchmarks

The `benchmarks` directory contains the static and experimental comparison of seven .NET data-access frameworks that preceded the tool: [Dapper](https://github.com/DapperLib/Dapper), [PetaPoco](https://github.com/CollaboratingPlatypus/PetaPoco), [RepoDB](https://github.com/mikependon/RepoDB), [linq2db](https://github.com/linq2db/linq2db), [NHibernate](https://github.com/nhibernate), [Entity Framework Core](https://github.com/dotnet/efcore), and [Entity Framework 6](https://github.com/dotnet/ef6). Benchmarks run against the Microsoft SQL Server [WideWorldImporters](https://learn.microsoft.com/en-us/sql/samples/wide-world-importers-what-is) sample database; see [`benchmarks/README.md`](benchmarks/README.md) for setup.

The measured output of that comparison is **not versioned** ([decision 042](docs/decisions/042-measured-benchmark-output-out-of-git.md)): it is a single run from March 2025, and the exclusion covers the whole directory — the measurements and the R script that renders the charts from them, as much as the charts themselves. A clone therefore contains the benchmark projects and their description, not their results; earlier revisions still hold them, so `git show <commit>:benchmarks/results/…` retrieves any of it.

## Beyond this version

What remains is sorted into five categories, and the marker saying which item is being worked on right now sits with the item itself, in [`docs/open-items.md`](docs/open-items.md).

- **Next up.** A short queue of items that each either make a statement in the architecture description untrue or leave silently wrong output behind — and after them the review and the `2.0.0` release that close the row.
- **The Advisor and the experiments.** Extending the Advisor beyond Dapper and EF Core to every supported framework, and the experimental part that stands on its measurements. Both are exempt from the guarantees above as they stand, and this is the milestone the MAJOR after `2.0.0` is reserved for.
- **The interface.** Batch input, and displaying the intermediate representation, which requirement F14 names and this version does not claim at all.
- **Useful, not required.** A second database dialect; reproducibility of the build itself, meaning a dependency lock file, base images and CI actions pinned by digest rather than by a moving tag, and style rules enforced by CI rather than merely present in the repository; and a persistent identifier for a release.
- **Leftovers.** Documented gaps and unanswered questions nobody is working on, written down so that what the tool does not claim about its frameworks is on the record.
